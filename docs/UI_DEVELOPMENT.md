# 界面开发约定

Steer 有三个界面：OpenWrt 的 LuCI、Linux 网页、macOS SwiftUI。导航、布局、控件、登录方式可以各按平台习惯来，但协议字段、配置约束、引用关系、操作结果和平台能力只能有一份共享定义。三端之间的差异只应该来自平台本身，不应该来自三份手抄的规则。

## 分层

```text
Canonical Intent / Validate / Compiler
                  │
          共享界面描述（uispec）
                  │ 构建时生成
        ┌─────────┼──────────┐
        ↓         ↓          ↓
      LuCI     Linux 网页   SwiftUI
        │         │          │
      ubus      HTTP      control socket
        └─────────┼──────────┘
                  ↓
           共享的操作接口
                  ↓
            各平台适配器
```

- 配置合不合法，最终由 `intent` 和平台的 `Validate` 说了算。界面不要再写一套完整的校验。
- `internal/uispec` 定义所有可编辑字段、控件类型、枚举、显示条件、敏感字段和平台能力，是界面描述的唯一来源。
- 生成的 JavaScript/Swift 文件不要手改，改 `internal/uispec` 然后重新生成。
- 界面只负责显示、编辑草稿和调用后端。Apply、订阅合并、测试、Geo 分类是否合法，都由后端决定。
- 三端的传输方式不同，但同一个操作的请求、结果和错误含义要一样。

## 必须共享的内容

下面这些不要在某个界面里单独写死：

1. 节点协议列表、显示名、字段、默认值、必填条件、枚举、TLS/传输能力，以及切换协议时哪些字段可以保留；
2. 引导 DNS、DNS 配置、本地代理和规则里的协议枚举；
3. 规则的匹配字段、嗅探协议、默认规则的固定含义、Geo 前缀；
4. 直连/拒绝/single 路由类型和 `detour` 的约束（拒绝路由为兼容旧配置仍写作 `kind=block`）；
5. 各类对象的 ID 生成方式、是否只读、能否排序、删除时怎么检查引用；
6. 平台能力的名称和不支持的原因；
7. 操作结果里的 `saved`、`applied`、`revision`、`validation`、`status` 和结构化错误。

几个具体约定：

- `id_policy`：普通对象的 ID 由界面自动生成，`name` 只是可选的显示名。LuCI 仍然用命名 section，但新建时不需要用户自己想 ID。
- `creation_defaults` 和 `creation_required_fields`：新建对象时要把默认值真正写进草稿或 UCI，不能只靠控件显示一个默认值。目前的默认值是 SOCKS/1080 节点、UDP/53 DNS 配置、只监听回环地址的 Mixed/1090 本地入口。用户已有的值或者改过的值不能被默认值覆盖。
- 引用列表里，名字重名时才追加服务器地址、来源或短 ID 来区分，平时只显示名字。
- 界面描述只描述用户能看懂的含义，不要放 UCI section、systemd 单元、launchd label、HTTP 路径、socket、CSS 或 SwiftUI 布局。

## 各平台保留自己的东西

- LuCI：`form.Map`、`GridSection`、UCI 待提交修改、LuCI 会话和 ACL。
- Linux：只监听本机的网页、Bearer token、ETag、浏览器的无障碍支持。
- macOS：`NavigationSplitView`、`Table`、`Form`、管理员授权、系统组件安装页。
- 字段怎么分页分组、列表密度、弹窗、拖拽、帮助文字由各平台自己决定。CSS、SF Symbols、LuCI 主题这些不需要统一。

## 普通页面显示什么

普通页面是给用户配置和运维用的，不是后端数据的转储。字段能安全传输，不代表它适合显示出来。新加任何用户看得见的内容，先想清楚它能帮用户在这个页面做什么判断或操作；想不清楚就别加。

总览、基础设置、对象列表、编辑器和状态栏里默认不放：

1. 原始 JSON、数组、接口原始响应、逐项诊断数据、完整错误链、没整理过的日志；
2. 内部 ID、digest、配置目录路径、临时核心名、outbound tag、进程参数、命令行、socket、服务名；
3. 带纳秒的时间戳、原始 URL 路径和参数、空字段占位、对用户没意义的计数和阶段名；
4. 不限条数的历史、重复的警告、每个对象一张的同类状态卡片、默认展开的技术细节；
5. 解释内部流程的长篇说明。文案只讲当前状态、影响、下一步该做什么，以及必要的限制；
6. 凭据、私钥、token、订阅原文等敏感字段，连打码后的占位也不要显示。

应该显示的是：用户起的名字、协议和服务器这类认得出的摘要、成功还是失败、影响范围、发生时间、下一步操作。时间用本地化或相对时间；没有的字段直接不显示；机器输入用等宽字体，普通文字用系统字体。自定义容器要有内边距，文字不要贴边。不要用 `visibility: hidden`、透明文字或移出屏幕的方式藏重复内容，应该删掉重复的那一份。

具体规则：

- **警告**：先按候选配置或当前运行配置里实际用得到的对象过滤，完全没用到的节点、路由、DNS 配置不产生警告。普通页面按类型汇总显示数量，不逐条列出。错误照常严格报告，不能借过滤藏起来。
- **警告分组**：共享校验输出 `warning_groups`，按 `code/object_type/option` 分组，带受影响的数量、安全的摘要和跳转目标。三端的总览只负责翻译和跳转，不读 `object_id` 或原始 `message`，也不自己重新算「规则 → DNS 配置/路由 → 节点/前置代理」的引用关系。`main.enabled=false` 时没有运行警告。
- **测试结果**：普通页面不显示历史报告。每个网络/节点/路由测试入口只显示该类测试最近一次的时间、结果和一个主要指标；配置变了就标「已过期」。
- **测试结果格式**：由共享 Go 层生成 `scope/object_id/kind/tested_at/ok/stale/summary/metric_value/error_summary`，三端各有一个批量读取接口。界面本地化时间、显示摘要，并按可选的 `metric_value` 排序（连接是毫秒，下载是 Mbps）。未保存的草稿不改变测试依据的已保存配置，界面不能自己标过期。测试失败时也要立刻用返回的结果，或者重新读取。
- **全局状态区**：只显示运行状态、草稿/已保存/运行中之间必要的差异，以及能点的操作。不显示 digest、generation、候选配置路径或 Apply 内部阶段。状态和操作放在同一个容器里，不要变成贴边的一行小字。
- **同一件事只在一个地方完整显示**：总览给摘要和跳转，对象页显示对象自己的结果，系统页显示安装和运行信息，高级页显示用户主动要看的高级数据。

例外只限于以下几种，不要扩大：

- 系统页可以显示排错、安装、修复、卸载需要的版本、组件、配置目录、状态目录、socket 路径、服务名和当前运行配置的摘要。要分组、有名字、去掉敏感信息、可以复制，不要直接倒后端对象或日志。
- 高级页可以在用户主动打开后显示 Canonical JSON 编辑/预览和必要的内部 ID。敏感字段仍然默认隐藏；原始错误链、命令行、不限量的日志不因为是「高级」就能放。
- 日志只能作为二级排错入口按需加载，要去敏感信息、限制条数、标明来源，不能默认展开，也不能代替给用户看的错误摘要和恢复操作。

代码评审和契约测试要拦住这些写法：把后端对象直接丢给通用的卡片渲染器；对 reports/warnings/logs 不加限制地 `map` 成 DOM；在普通页面加内部 ID/digest/路径；用 CSS 截断掩盖太长的内容；删了文字却留下空容器。测试至少要用大订阅的警告、重复的测试报告、长错误链、空字段和含敏感值的数据，验证普通页面只显示有限、安全的摘要。系统页和高级页的例外单独测试，不能因此放宽普通页面。

## 页面结构

三端页面的职责和顺序一样，用户换平台不用重新找功能在哪。Linux 和 macOS 可以显示分组标题；LuCI 要把分组摊平成 Steer 下面的一层菜单，避免主题导航、分组和表单 tab 叠成三层。

```text
状态
  └─ 总览
配置
  ├─ 基础设置
  ├─ 节点
  ├─ 路由
  ├─ DNS 配置
  ├─ 本地代理
  └─ 规则
服务
  ├─ 订阅
  ├─ 诊断
  └─ 系统
高级
  └─ 高级配置 / Canonical 预览
```

- **总览**固定五块：运行方式、配置状态（草稿/已保存/运行中）、当前草稿里六类对象的数量（节点、路由、DNS 配置、本地代理、规则、订阅）、草稿的校验结果和汇总警告、最近一次 Apply 和快捷操作。已保存/运行中/待应用必须来自后端的真实状态，不能用草稿或最近一次 Apply 冒充。保存、应用、放弃这些按钮可以放在同页的全局状态区，不要再复制一套。
- **基础设置**只编辑全局选项、测试网址、DNS 缓存和引导 DNS。
- **节点**和**路由**是两个页面。订阅状态和更新不放在节点页。
- **诊断**放网络测试和最新结果摘要、校验结果、当前运行配置的 53 端口检查、最近一次 Apply、按需加载的日志，以及刷新按钮，不放历史报告。节点和路由的最近测试结果放回各自的操作旁边。
- **系统**显示版本、schema、generation、最近一次 Apply、Geo 数据、sing-box 编译选项、DNS 接管范围、平台路径和平台特有的组件/安装功能。
- **高级**：JSON 平台提供 Canonical 编辑，OpenWrt 提供只读预览。它不是结构化页面缺字段时的兜底。
- 平台特有的功能放进最接近的共享页面，不要为单个平台加顶层导航。

导航信息也由界面描述生成，三端可以翻译标题、用不同图标。Linux/macOS 的分组、三端的页面 key 和顺序由契约测试保证一致；LuCI 的菜单是按分组顺序展开后的一层列表，分组本身不要有可访问的 URL。

## 功能基线和平台能力

三端都要有：

- 状态、启用/禁用、校验、保存、Apply，以及「已保存但 Apply 失败」这种部分成功的明确反馈；
- 全局设置、引导 DNS、节点、路由、DNS 配置、本地代理、规则和订阅的结构化编辑；
- 所有节点协议都有能填完整的表单；
- 节点导入、Geo 分类列表、订阅状态/更新/清理过期节点；
- 直连/代理/下载测试、单个节点、批量节点和路由链测试；
- generation、最近一次 Apply、Steer/sing-box/schema/Geo 的运行信息；
- 版本冲突保护，或者和平台单写者模型等效的保护。

平台差异通过能力声明表达：

- macOS 不支持 `source_mac_address`，界面要说明原因，不能假装支持；
- Canonical JSON 原文编辑只在 JSON 平台有；OpenWrt 只给只读预览，UCI 仍是唯一的配置；
- 系统组件安装/升级只在 macOS 有；
- macOS 接管物理网络服务的系统 DNS；进入 TUN 的流量按「53 端口劫持 → ICMP → 私网直连 → 嗅探 → 解析 → 用户规则」处理，网络服务变化由平台的 DNS 看护处理；
- LuCI ACL、Linux token、macOS peer credential 是传输层的权限，不进共享配置；
- 日志来源和订阅调度是平台自己的实现，但用户看到的操作和结果要一致。

后端没声明的操作不要显示。不能用的功能隐藏或禁用，并给出固定的原因，不要用一段说明文字假装功能已经实现。页面行为由 Node 和 Swift 测试验证，生成文件和 LuCI 菜单由一致性检查验证。

## 列表和操作

- 节点按「手动节点 / 订阅」分组。订阅节点只读，不要显示点了也没用的编辑、删除或启用开关。
- 节点和 single 路由的每一行都有连接测试和下载测速。批量测试只测当前分组里可见且启用的节点。
- 单行测试、批量测试、订阅更新、清理过期节点时，只禁用正在执行的那个操作，不要锁住整张表或阻止滚动。停用的对象不要提供后端一定会拒绝的操作。LuCI 有未提交的 UCI 修改时，不能拿已提交的节点/路由去测。
- 三个网络测试读已保存的网址、用当前网络直接访问，不因为 Steer 没启用或没有运行配置而禁用。临时核心名、outbound ID、命令行、原始 URL、digest/generation、完整错误链不要出现在普通测试结果里。
- 直连路由是必需的，始终启用；拒绝路由类型固定但可以启停。两者都不能删除、拖动排序或改类型，新建路由只能是 single。拒绝只编译成 sing-box 的 `reject` 动作，不生成已废弃的 `type=block` 出站。
- 删除订阅前先检查它的节点有没有被路由引用；没有的话，订阅和它的节点一起从草稿里删掉。
- 订阅更新的提示要同时显示新增/现有/过期/跳过的数量，并说明：节点列表已更新、正在运行的配置没变、没被引用的消失节点已删除、被路由引用的保留为过期。过期警告提醒尽快换掉引用；清理只能删已经没有引用的过期节点，不会顺带改路由。
- 节点导入和导出都用共享的后端解析器：导入支持多行分享链接和 Base64 文档，导出用当前草稿并提示包含完整凭据。文案不要说是在前端解析或拼接的。
- LuCI 批量导入在写入 UCI 之前，逐条显示名称、协议、服务器、TLS 校验状态和是否带凭据；凭据内容不进预览的 DOM，取消时不创建任何 section。JSON 的布尔值和 UCI 的 `"1"` 用同一套转换。
- LuCI 的命名 `GridSection` 保留原生流程：临时 section → 编辑弹窗 → 保存/取消。ID 按共享规则生成，默认值在 `data.add()` 时写入；新建后马上进入编辑，取消就删掉临时 section，不要先 `map.save()` 留下一行空的待提交记录。
- 删除保护统一看 `collection_references`：节点 ← 路由的 node；路由 ← 规则的 route 和路由的 detour；DNS 配置 ← 规则的 dns_profile；本地代理 ← 规则的 inbound。删除前列出引用并可以跳过去。订阅和过期节点沿用节点的引用保护。后端校验是最后一道关，不做级联删除。
- 规则摘要要覆盖所有 `rule_match_fields`。`rule_connection_only_fields` 说明 `ip_match/network/protocol/port` 不参与 DNS 配置的选择；规则只有这些条件时，三端都显示「DNS 继续匹配后面的规则」。macOS 要显示来源 MAC 不可用的原因，不能直接藏掉。

## 敏感数据

- 分享链接、节点密码、私钥、网页 token 和订阅原文不写日志。
- 敏感内容不通过进程参数传，只能用请求正文、标准输入、权限受限的临时文件或已鉴权的本地 socket。
- 导入预览默认隐藏凭据，用户确认后才写入草稿。
- 界面描述只能把字段标成敏感，不能带任何配置值。

## 操作结果

所有写操作都要区分「保存了没有」和「应用了没有」：

```json
{
  "saved": true,
  "applied": false,
  "revision": "sha256-…",
  "validation": { "ok": true, "errors": [], "warnings": [] },
  "apply_result": { "ok": false, "error": "…" }
}
```

配置已经保存但 Apply 失败时，界面要明确说是部分成功，并把草稿的 revision 更新到磁盘上的版本，不能退回「未保存」，也不能暗示旧配置还是已保存的那份。

保存和 Apply 的结果里带完整的 `validation.errors/warnings`（含 `code/object_type/object_id/option/message`），但传过来不等于要全部显示。结果面板跟当前草稿绑定，草稿一改，旧的「通过/失败」立即清掉。点错误要能打开对应对象并定位到字段；警告先按实际用到的对象过滤，再按类型汇总。普通页面不显示内部 ID、原始 message 数组或凭据。

最近一次 Apply 是一条单独的记录。后端保留候选配置的身份、时间、结果和错误摘要；普通界面只显示本地化时间、结果和安全的摘要，候选配置路径或 generation 只在系统页显示。候选配置不能被当作当前运行配置。

**全局启用开关**（三端一样）：只操作最新的已保存配置，在和订阅更新共用的锁里完成读取、修改 `enabled`、保存、应用。草稿格式有错也不影响启停。草稿没改过的，操作完成后同步成新的已保存配置；改过的保留原样和原来的 revision，之后显式保存时照常检查冲突。

**Linux 网页**

- 草稿、已保存、运行中分开显示：`dirty` 只说明浏览器里的草稿，revision 属于已保存配置，运行中的 generation/digest 只来自 `/run/steer/current`。
- 保存后即使草稿干净了，只要已保存配置编译出来的运行部分和当前运行的不一样，或者上次同样配置的 Apply 失败了，「应用已保存配置」仍然可点。订阅刷新带来的、没被路由引用的节点不算进运行部分，只显示节点列表的提示，不会出现「待应用」。
- 「高级」页的 JSON 和结构化页面共用一份草稿。文本框输入立即进入草稿并标记已修改；JSON 写错时保留原文、禁止保存和切到结构化页面，不能拿一份旧的解析结果冒充当前表单。顶部和高级页里的保存按钮调用同一个操作。有修改时顶部有带确认的「放弃修改」，确认后走唯一的重新载入流程；取消不改草稿。
- 每次修改草稿都分配一个递增的 epoch。保存时发送快照，响应只能清掉同一个 epoch 的修改标记，保存期间新的修改仍算未保存。保存、应用、重新载入互斥，重复点击或乱序返回的响应不能覆盖更新的内容。订阅更新/清理也记下开始时的 epoch，期间草稿变了就只刷新节点列表提示，不自动重新载入，也不能让旧页面的渲染覆盖当前页面。
- 页面可见时定期刷新已保存配置的 revision 和运行状态。发现外部改了配置：有修改的草稿不替换，只提示冲突；干净的草稿由用户点一下重新载入。手动刷新、定时刷新、保存后刷新都用同样的比较逻辑。

**macOS**

- 读取配置时同时拿到 revision，保存和应用都带上 `expected_revision`。版本冲突时不能改已保存配置、运行中配置或本地草稿；界面提供「重新载入」「保留本地草稿」「强制覆盖」三个选择。手动更新订阅结束后，只有草稿没变过才自动重新载入，否则走同样的冲突选择。订阅更新从不自动 Apply。
- 每次启动 App 只初始化一次草稿。所有页面和菜单栏共用保存、应用已保存配置、保存并应用；「应用已保存配置」只应用磁盘上的配置，不夹带草稿。
- 工具栏的启用开关通过单独的 control 命令只改已保存配置的 `enabled` 并应用，未保存的草稿保留原文和 revision。状态查询也通过 control 服务读取，读取失败不能当成服务已停止。
- 重新载入、安装/修复、退出这些会替换或丢弃草稿的操作，统一走「保存 / 放弃 / 取消」确认。安装完成后默认保留草稿；Apply 失败时要分别显示已保存配置里的开关和后端实际的运行状态。

**LuCI**

- 待提交、已保存、运行中分别来自当前 rpcd 会话里的 UCI 修改、已提交的 UCI、`/run/steer/current`。
- 每个 Steer 页面共用带启用开关的状态区。开关通过单独的 RPC 只改已提交 UCI 的 `enabled` 并直接 Apply，不保存页面表单或会话里待提交的修改；基础设置页没有第二个总开关。
- 待提交的「禁用」不能盖住还在运行的配置。Apply 失败且没有待提交修改时，要能「应用已保存配置」重试。
- `pending_apply` 比较的是编译后的运行部分，不是整份配置的 digest，所以没被引用的订阅节点变化不会触发「待应用」，也不产生运行警告。

## 生成和测试

运行 `go generate ./internal/uispec`（在 `go/` 目录下）生成 LuCI、Linux 网页和 SwiftUI 用的界面描述文件，生成的文件要一起提交。CI 会检查重新生成后没有差异，并验证：

1. 每个可选的节点协议都能按描述构造出一份通过共享校验的配置；
2. Canonical 配置的每个用户字段都在描述里，或者被标为内部/平台不支持；
3. 三端生成文件的 schema 和 digest 相同；
4. 声明为支持的能力，在平台后端有对应的契约测试；
5. 界面上能看到的操作，后端都有实现；
6. OpenWrt、Linux、macOS 各自的界面回归测试通过。

新增或修改字段的顺序：Canonical 模型和校验 → `internal/uispec` → 重新生成 → 三端界面接入 → 契约测试。不要先在某一个界面上加字段，再回头补其他平台。
